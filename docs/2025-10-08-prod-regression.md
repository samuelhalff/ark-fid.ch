# 8 Oct 2025 production regression notes

## What changed between 7 Oct and 8 Oct
- 7 Oct (`src/i18n.ts.backup`) kept the entire translation catalogue in the bundle by statically importing every JSON file per locale/namespace. The client had all strings synchronously when `useTranslation()` ran. 【F:src/i18n.ts.backup†L1-L74】
- 8 Oct (`src/i18n.ts`) replaced the static catalogue with a custom dynamic backend that tries to lazy-load translations at runtime via `import(\`@/src/translations/${locale}/${namespace}.json\`)`. 【F:src/i18n.ts†L1-L88】
- The same refactor customised the client webpack `splitChunks` strategy so every translation JSON becomes its own async chunk (`translations-${locale}-${namespace}`). 【F:next.config.js†L12-L37】

## Why this likely breaks the production build
1. **Dynamic translation imports can be pruned in the standalone bundle.** In dev, webpack resolves the template literal and streams the JSON files on demand. Inside the standalone production bundle that dynamic context can be tree-shaken, so `DynamicBackend.read()` falls through to the catch block (`Failed to load translation`) and returns `{}`. Once `useTranslation()` receives an empty resource store our deferred client islands (`HeaderControls`, `MobileMenu`) render nothing even after hydration, which matches the missing language/theme toggles that only exist inside those islands. The same failure path explains why `TranslatedTextArray`/`TranslatedObjectArray` return fallbacks or blanks on the accounting page. 【F:src/i18n.ts†L31-L85】【F:src/components/navigation/NavbarServer.tsx†L64-L96】【F:src/components/ui/translated-text-array.tsx†L1-L44】
2. **Client-only sections gate their styling behind those islands.** With the translation promise rejected, we never mount the hero/services client components that request the abstract background assets, so the prod build falls back to the unstyled background even though the Tailwind rules still exist. 【F:app/layout.tsx†L225-L315】【F:app/globals.css†L80-L143】
3. **`getTranslations()` still reads from the filesystem.** The refactor did not move translations into `public/`, so every SSR call hits `process.cwd()/src/translations`. That only works in environments where the deploy script copies the raw JSON into the standalone output; the base `npm run prod` target in `package.json` does that, but any environment that skips the copy (e.g. a fresh Vercel preview) would now render empty breadcrumbs/services metadata because the files no longer ship with the app bundle. 【F:src/lib/i18n.ts†L20-L71】【F:scripts/prepare-artifact.sh†L45-L78】

## Recommendations
1. **Revert the i18n loader for now.** Restore the pre-refactor `src/i18n.ts.backup` (or feature-flag the dynamic backend) so we unblock prod. Then profile again to quantify the real TBT cost before attempting another lazy-loading approach.
2. **If we retry lazy loading, switch to `i18next-http-backend`.** It works with Next.js app router and keeps webpack from guessing dynamic import contexts. We can serve the JSON out of `/public/locales` or an API route, which removes the need for filesystem reads in prod.
3. **Undo the custom `splitChunks` override.** Let Next handle chunking until we confirm a lazy-loading strategy that works with `standalone`. If we do add a cache group later, guard it behind `if (process.env.NODE_ENV === 'development')` first so prod is safe.
4. **Add a smoke test that runs `npm run prod` and requests `/fr/` and `/fr/services/accounting/`.** We can assert that the response still contains the language toggle markup and a known accounting translation string. That would catch the regression automatically.
